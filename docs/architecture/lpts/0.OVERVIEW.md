# 0. Overview: LPTS from 10,000 feet

LPTS means **Logical Plan To SQL**.
It is a DuckDB extension that takes a DuckDB `LogicalPlan` / `LogicalOperator`
tree and serializes that plan back into SQL.
The generated SQL is not the user's original text.
It is SQL reconstructed from the plan DuckDB would execute.

The most useful mental model is:

```text
DuckDB SQL input
  -> DuckDB parser, binder, planner, optimizer
  -> optimized LogicalOperator tree
  -> LPTS AST
  -> flat CTE list
  -> emitted SQL string
```

OpenIVM uses LPTS as a compiler backend.
OpenIVM rewrites a view plan into a delta-maintenance plan, then asks LPTS to
turn that rewritten plan into SQL that a caller can execute.
For plain DuckDB, the emitted SQL can be DuckDB-shaped.
For openivm-spark, OpenIVM asks for Spark-shaped SQL and openivm-spark applies a
final post-processing layer before sending statements to Spark.

## 0.1 Scope of this chapter

This chapter is the map before the terrain.
It explains what LPTS is, why it exists, how the three pipeline phases fit
together, how dialect targeting works, and where openivm-spark extends the
contract.

It intentionally avoids operator-by-operator details.
The later chapters should be read for the AST node taxonomy, expression
serialization, flattener edge cases, dialect hooks, and round-trip testing.

In the current source tree, the first two implementations live together in
`src/lpts_pipeline.cpp`, while final CTE serialization lives in
`src/cte_nodes.cpp`.

## 0.2 What LPTS is

LPTS is a DuckDB extension for optimized-plan inspection and cross-system SQL
compilation.
The README describes it as a DuckDB extension for "optimized-plan inspection"
and "cross-system SQL compilation" that reconstructs equivalent SQL from
DuckDB's post-optimizer logical plan as a sequence of named CTEs
(`README.md:1-9`).

The public extension entry point registers a loadable extension named `lpts`.
The C++ extension entry macro calls `LoadInternal(loader)` and the extension
name method returns `"lpts"` (`src/lpts_extension.cpp:323-345`).

From a user's perspective, the most direct interface is:

```sql
LOAD 'build/release/extension/lpts/lpts.duckdb_extension';
PRAGMA lpts('SELECT name FROM users WHERE age > 25');
```

The result is a SQL string.
For a simple filtered projection, it is usually a `WITH ... SELECT ...` program
whose intermediate CTEs correspond to logical operators such as scan, filter,
projection, join, aggregate, order, or limit.

From OpenIVM's perspective, the input is often not a user's SELECT anymore.
OpenIVM has already rewritten the logical plan into an incremental refresh plan.
LPTS is the final serialization bridge from that rewritten DuckDB logical plan
back to executable SQL.

## 0.3 What LPTS is not

LPTS is not a source-code formatter.
It does not preserve comments, whitespace, aliases, or the original CTE layout.
It serializes an optimized logical plan, so optimizer rewrites are expected to
show up in the output.

LPTS is also not DuckDB's internal plan serializer.
DuckDB has its own internal representations and stringification paths for
planning, debugging, and execution.
Those are not designed as a stable, human-readable, portable SQL emission layer.
LPTS exists because OpenIVM and similar callers need a SQL program that can be
fed to another SQL engine after plan-level rewriting.

The README calls out the same limitation directly:
LPTS reconstructs the optimized plan, not the original SQL text, and it does not
preserve formatting, alias spelling, or original CTE structure
(`README.md:78-85`).

## 0.4 Why LPTS exists

OpenIVM is a SQL-to-SQL incremental view maintenance compiler.
Its rewrite rules work naturally on DuckDB logical plans.
The final maintenance program, however, must be executable SQL.
Without LPTS, OpenIVM would have to hand-generate SQL in every rewrite rule or
expose DuckDB's internal plan objects to the caller.

LPTS solves that impedance mismatch.
It lets OpenIVM say:

1. Build a normal DuckDB logical plan.
2. Rewrite that plan into a delta plan.
3. Serialize the rewritten plan into SQL.
4. Return that SQL to the caller.

This is especially important for openivm-spark.
The Spark extension launches the DuckDB CLI with the OpenIVM extension loaded,
passes `target_dialect="spark"` in the CompileFacts JSON, and asks
`openivm_compile_with_facts` for a multi-statement refresh program.
OpenIVM then uses LPTS internally to serialize pieces of that program.
The Spark side receives text, not DuckDB plan objects.

Dialect targeting is the other reason LPTS exists.
DuckDB's plan knows semantics, but syntax differs across engines:
identifier quoting, fully-qualified table names, function names, casts, window
frame support, interval literals, and table function aliases all vary.
LPTS provides configurable dialect hooks so the same plan can be emitted as
DuckDB, PostgreSQL-ish, or Spark-ish SQL.

## 0.5 The three-phase pipeline

The core pipeline is declared in `src/include/lpts_pipeline.hpp`:

```cpp
unique_ptr<AstNode> LogicalPlanToAst(ClientContext &context,
                                     unique_ptr<LogicalOperator> &plan,
                                     SqlDialect dialect = SqlDialect::DUCKDB);

unique_ptr<CteList> AstToCteList(const AstNode &root,
                                 SqlDialect dialect = SqlDialect::DUCKDB);
```

Those two public functions cover phases 1 and 2.
Phase 3 is `CteList::ToQuery(...)`, declared in `src/include/cte_nodes.hpp` and
implemented in `src/cte_nodes.cpp`.

The whole path is therefore:

```text
LogicalOperator tree
  -> LogicalPlanToAst(...)
  -> AstToCteList(...)
  -> CteList::ToQuery(...)
  -> SQL string
```

The implementation guide in the LPTS repository summarizes the same flow as:
`Logical Plan -> AST -> CTE List -> SQL String` (`IMPLEMENTATION.md:1-8`).

### Phase 1: `AstBuilder`

`AstBuilder` walks DuckDB's logical plan and builds an AST.
The AST is an intermediate representation that is much closer to SQL than a
DuckDB `LogicalOperator`, but it is still not final SQL.

The AST layer captures semantic content:

- table names and scan columns;
- pushed-down table filters;
- projection expressions;
- aggregate expressions and grouping columns;
- join types and join conditions;
- set operations;
- order, limit, distinct, and top-N nodes;
- materialized CTE references;
- delim joins used for decorrelated subqueries;
- recursive CTE structure.

`src/include/lpts_ast.hpp` states this explicitly: the AST is a
"dialect-agnostic intermediate representation" between DuckDB's
`LogicalOperator` tree and the flat CTE list used for SQL generation
(`src/include/lpts_ast.hpp:12-20`).

The current implementation defines an `AstBuilder` class in
`src/lpts_pipeline.cpp`.
Its constructor receives a `ClientContext` and `SqlDialect`, and its `Build`
method marks referenced aggregate/projection bindings before recursively walking
the plan (`src/lpts_pipeline.cpp:2484-2494`).
The public `LogicalPlanToAst` function simply creates that builder and calls
`Build` (`src/lpts_pipeline.cpp:2497-2503`).

The dialect is already visible in phase 1 because some expression serialization
needs dialect-specific names.
For example, the pipeline source has dialect-specific function remapping for
PostgreSQL and Spark (`src/lpts_pipeline.cpp:908-916`), and Spark-specific
window limitations for `GROUPS` frames and `EXCLUDE` clauses
(`src/lpts_pipeline.cpp:793-810`).

### Phase 2: `AstFlattener`

`AstFlattener` converts the AST tree into a flat ordered list of CTE nodes.
This phase is where tree shape becomes `WITH cte_0 AS (...), cte_1 AS (...)`.

The flattener walks bottom-up / post-order.
That ordering matters because a CTE can only reference CTEs defined before it in
the `WITH` list.
Scans become `scan_N`, filters become `filter_N`, projections become
`projection_N`, aggregates become `aggregate_N`, joins become `join_N`, and so
on.
The CTE naming helper in `AstFlattener::CteName` implements those names for the
major node types (`src/lpts_pipeline.cpp:2549-2567`).

The current source describes the class as a phase-2 helper that walks the AST in
post-order and produces a flat `CteList` (`src/lpts_pipeline.cpp:2521-2530`).
It also stores dialect state, materialized CTE mappings, and delim-join source
mappings (`src/lpts_pipeline.cpp:2531-2547`).

Phase 2 is not just a mechanical tree flatten.
It handles plan shapes that do not map to naive post-order traversal:

- materialized CTE bodies must be emitted before their references;
- `CteRef` nodes become scans over the materialized CTE body;
- delim joins must register the outer CTE as the source for inner delim scans;
- recursive CTEs may require inline SQL for the recursive step;
- the dialect must be stamped onto every CTE node before final rendering.

The `StampDialect` helper propagates the flattener's dialect to every generated
node so `ToQuery()` can quote identifiers and render syntax consistently
(`src/lpts_pipeline.cpp:3205-3213`).
The public `AstToCteList` entry point instantiates an `AstFlattener` and calls
`Flatten` (`src/lpts_pipeline.cpp:3220-3223`).

### Phase 3: `CteList::ToQuery`

`CteList::ToQuery` emits the final SQL string.
It walks the already-ordered list of CTE nodes and renders each one with
`CteNode::ToCteQuery()`, then appends the final root statement.

`src/include/cte_nodes.hpp` documents the contract:
calling `ToQuery()` serializes the whole CTE list into a single SQL string
(`src/include/cte_nodes.hpp:398-414`).
The implementation writes `WITH` or `WITH RECURSIVE`, joins CTE definitions with
commas/newlines, renders the final node, and appends a semicolon
(`src/cte_nodes.cpp:357-390`).

The final node is usually `FinalReadNode`.
It maps generated CTE column names back to user-facing output names with a
closing `SELECT child_col AS final_col FROM child_cte`
(`src/cte_nodes.cpp:37-57`).
For insert plans, the root can be `InsertNode`, which renders `INSERT INTO ...
SELECT * FROM ...` (`src/cte_nodes.cpp:59-80`).

Each concrete `CteNode` owns its local SQL fragment.
Examples:

- `GetNode::ToQuery()` renders table scans and pushed-down filters.
- `FilterNode::ToQuery()` renders explicit column selection plus `WHERE`.
- `ProjectNode::ToQuery()` renders a projection over its child CTE.
- `AggregateNode::ToQuery()` renders `GROUP BY` and aggregate expressions.
- `JoinNode::ToQuery()` renders join syntax and special MARK-join handling.
- `UnionNode`, `ExceptNode`, and `CteSetOperationNode` render set operations.
- `OrderNode`, `LimitNode`, `TopNNode`, and `DistinctNode` render relational
  modifiers.

Those implementations live together in `src/cte_nodes.cpp:32-356`.

## 0.7 Public API and caller flow

There is no single exported C function named `LPTS_emit` in the current source.
The public C++ API is the composition of:

1. `LogicalPlanToAst(context, plan, dialect)`.
2. `AstToCteList(*ast, dialect)`.
3. `cte_list->ToQuery(use_newlines, output_names)`.

That is the practical `emit(LogicalPlan, dialect, options) -> string` API.
The declarations are in `src/include/lpts_pipeline.hpp:8-15` and
`src/include/cte_nodes.hpp:410-414`.

The extension wraps that API in SQL-facing entry points.
`PRAGMA lpts('query')` plans and optimizes the query, reads the dialect setting,
runs the pipeline, and returns `SELECT '<result>' AS sql;`
(`src/lpts_extension.cpp:100-125`).

The table function `lpts_query('query')` does the same thing but returns a proper
one-row table, which is useful in tests and programmatic SQL
(`src/lpts_extension.cpp:127-179`).

`PRAGMA lpts_exec('query')` returns the generated SQL directly as the substitute
query DuckDB should execute, so DuckDB executes the LPTS output and returns its
results (`src/lpts_extension.cpp:181-196`).

`PRAGMA print_ast('query')` and `print_ast_query('query')` expose the AST for
human debugging and tests (`src/lpts_extension.cpp:234-280`).

OpenIVM calls the C++ pipeline directly.
For example, OpenIVM reads `target_dialect` from CompileFacts, calls `LogicalPlanToAst`,
then `AstToCteList`, then `ToQuery` when serializing refresh SQL
(`src/upsert/refresh_sql.cpp:867-875` in the OpenIVM checkout).
It uses the same pattern when creating materialized views and building delta
insert plans (`src/core/parser.cpp:301-305`,
`src/rules/refresh_insert_rule.cpp:125-146` in the OpenIVM checkout).

## 0.8 Dialects supported

LPTS currently has three dialect enum values:

- `duckdb` / `DUCKDB`;
- `postgres` / `postgresql`;
- `spark`.

The enum is declared in `src/include/sql_dialect.hpp:13-17`.
`ParseSqlDialect` accepts the strings above and throws an error for anything
else (`src/lpts_pipeline.cpp:2508-2518`).
The extension setting is named `lpts_dialect`, defaults to `duckdb`, and is
registered with the description "Valid values: 'duckdb' (default), 'postgres',
'spark'" (`src/lpts_extension.cpp:286-292`).

Dialect behavior is distributed across the pipeline:

- Spark identifiers are backtick-quoted; DuckDB/PostgreSQL use DuckDB's optional
  double-quote helper (`src/lpts_helpers.cpp:9-27`).
- Fully-qualified table names use dialect-aware identifier quoting
  (`src/lpts_helpers.cpp:88-92`).
- PostgreSQL output strips DuckDB catalog/schema qualifiers in one flattener path
  (`src/lpts_pipeline.cpp:3048-3052`).
- Expression serialization remaps some function names for PostgreSQL and Spark
  (`src/lpts_pipeline.cpp:908-916`).
- Spark rejects unsupported window frame shapes early for `GROUPS` and `EXCLUDE`
  (`src/lpts_pipeline.cpp:793-810`).

The dialect system is intentionally incremental.
`duckdb` is the default and most native target.
`postgres` is described in the README as partial and still in progress
(`README.md:64-76`, `README.md:93-98`).
`spark` is the important target for openivm-spark, but it is best understood as
"close to Spark SQL", not the final Spark-executable dialect by itself.

## 0.9 The openivm-spark dialect extension

openivm-spark adds rules on top of LPTS's Spark dialect.
The boundary is:

```text
OpenIVM + LPTS Spark dialect
  -> close-to-Spark multi-statement SQL
  -> openivm-spark LptsSparkDialect.translate(...)
  -> Spark 3.5 / Delta Lake executable SQL
  -> SparkRefreshRewriter statement assembly
```

The openivm-spark chapter on `LptsSparkDialect` calls the upstream output
"LPTS-Spark" and says it is close to Spark SQL but not directly executable by
Spark 3.5 / Delta Lake 3.2 (`docs/architecture/openivm-spark/5-lpts-spark-dialect-postprocessor.md:6-18`).
It also notes that the current post-processor contains fourteen top-level
passes, despite the design note often calling them "~13 rewrites"
(`docs/architecture/openivm-spark/5-lpts-spark-dialect-postprocessor.md:20-23`).

Those post-processing gaps include:

- DuckDB/PostgreSQL postfix casts;
- DuckDB helper functions such as `count_star()` and `generate_series()`;
- macro bodies inlined by OpenIVM's Spark-function shims;
- SQL-standard timestamp suffixes not accepted by Spark in these contexts;
- quoted interval literal spellings;
- double-quoted identifiers that must become Spark backticks;
- `memory.main.` table prefixes that need Spark catalog/schema handling.

This layering is important.
LPTS should not grow every openivm-spark-specific text rewrite just because Spark
needs it for one refresh shape.
LPTS owns plan-to-SQL emission and broad dialect syntax.
openivm-spark owns the final compatibility shim for Spark 3.5 / Delta 3.2 and
its refresh rewriter.

## 0.10 `lpts_check`: round-trip correctness

`lpts_check` is the main correctness oracle for LPTS.
It takes input SQL, plans it, emits SQL through LPTS, and compares the original
query result with the emitted-query result.

In the current implementation, `PRAGMA lpts_check('query')`:

1. plans and optimizes the original query;
2. runs `LogicalPlanToAst`;
3. runs `AstToCteList`;
4. renders the generated SQL with `ToQuery(true)`;
5. normalizes the original first statement for subquery embedding;
6. compares both directions with `EXCEPT ALL`;
7. returns one boolean column named `match`.

The code constructs:

```sql
(A EXCEPT ALL B) has zero rows
AND
(B EXCEPT ALL A) has zero rows
```

where `A` is the original query and `B` is the LPTS-generated query
(`src/lpts_extension.cpp:199-232`).

That makes `lpts_check` a bag-equality test, not a string comparison.
It allows LPTS to change alias names, CTE layout, and formatting as long as the
result multiset is identical.
It can still fail for nondeterministic queries, unordered aggregates, or limit
queries with tied boundary rows; the source comments document that caveat
(`src/lpts_extension.cpp:201-207`).

The test README makes the project rule explicit:
every feature test needs a `PRAGMA lpts_check('<query>')` returning `true`
(`test/README.md:13-22`).
Existing SQLLogicTests pair `lpts_exec` concrete-result checks with
`lpts_check` bag-equality checks; for example, `test/sql/select.test` uses
`PRAGMA lpts_exec` for visible rows and `PRAGMA lpts_check` for round-trip
truth (`test/sql/select.test:13-80`), and `test/sql/pragmas.test` exercises
`lpts_exec`, aggregates, filters, joins, and `UNION ALL`
(`test/sql/pragmas.test:13-86`).

Chapter 7 of this architecture series covers `lpts_check` in depth.
This overview only needs the key point: LPTS is trusted when the generated SQL
re-parses, executes, and returns the same bag of rows as the original query.

## 0.11 How OpenIVM uses LPTS

OpenIVM has two major uses for LPTS.

First, at materialized-view creation time, OpenIVM can normalize the stored view
query by converting the planned query through LPTS.
When Spark asks for a compile, the per-call CompileFacts payload supplies the
`target_dialect` value that the LPTS pipeline uses so final column aliases match
the MV output names.

Second, at refresh compilation time, OpenIVM serializes rewritten delta plans.
The refresh SQL path checks for an empty delta plan, otherwise runs the LPTS
pipeline and stores the generated refresh SQL text
(`src/upsert/refresh_sql.cpp:860-875` in the OpenIVM checkout).

The OpenIVM CompileFacts `target_dialect` key is separate from LPTS's standalone
`lpts_dialect` setting.
Valid values remain `duckdb`, `postgres`, and `spark`, and both paths delegate to
LPTS's dialect parser.

openivm-spark drives this path by passing the Spark target dialect in the
CompileFacts JSON.
The Spark-side compiler chapter documents that the CLI script loads OpenIVM,
creates empty source tables, creates the DuckDB materialized view, and runs
`openivm_compile_with_facts` with
`{"target_dialect":"spark","compile_only":true,"force_view_delta_cascade":true}`.
The returned SQL then passes through `LptsSparkDialect.translate` and
`SparkRefreshRewriter` before Spark executes it.

## 0.13 Summary

LPTS is the SQL emission layer that makes plan-level rewriting usable outside
DuckDB internals.
It takes a DuckDB logical plan, builds a SQL-like AST, flattens that AST into a
CTE program, and renders dialect-targeted SQL.

For standalone DuckDB users, LPTS is a plan-inspection and round-trip tool.
For OpenIVM, it is a compiler backend.
For openivm-spark, it is the upstream half of a two-stage dialect bridge:
LPTS emits Spark-ish SQL from DuckDB plans, and openivm-spark performs the final
Spark/Delta compatibility rewrites before execution.
